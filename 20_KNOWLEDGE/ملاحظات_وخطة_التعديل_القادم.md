## 🔴 مشكلة #1: «تشغيل الاختبارات الوهمية» يعطي «لا نتائج» فوراً

### الصفحة
`19_PROTECTION/index.html` (بوتات الحماية)

### السبب الجذري (شخّصناه)
زر «🧪 تشغيل الاختبارات الوهمية» يستدعي 4 بوتات:
`GMTWarden.runProbes` · `GMTIntegrationTests.run` · `GMTAutoTest.run` · `GMTSelfTest.run`

الاختبارات الوهمية (probes) في gmt-warden **تحتاج اتصالاً حياً بـSupabase**:
- `probe-db-write` → يكتب/يقرأ/يحذف من جدول `error_log`.
- `probe-counter` → يستدعي دالة `increment_settings_counter`.

**إذا لم تتوفّر المفاتيح أو الجدول → كل اختبار يرجع `{ok:false, msg:'لا مفاتيح'}` → النتيجة تبدو فارغة أو ناقصة.**

### الاحتمالات (تحتاج فحصاً حياً لتأكيدها)
1. **صفحة البوتات لا تحمّل مفاتيح Supabase** (لأنها صفحة أدوات، ليست صفحة عمل). المفاتيح في gmt-config (مدمج بـcore)، لكن ربما لا تُضبط `window.GMT_CONFIG` بهذه الصفحة.
2. **جدول `error_log` غير موجود** بالقاعدة (يحتاج SQL).
3. **دالة `increment_settings_counter` غير موجودة** (SQL-1).

### خطة التعديل المقترحة (للمراجعة)
- **الخيار أ:** جعل الاختبارات الوهمية تعرض رسالة واضحة بدل «لا نتائج»: مثلاً «الاختبارات تحتاج مفاتيح القاعدة — افتحها من صفحة عمل (نقطة البيع) أو أضف المفاتيح هنا».
- **الخيار ب:** إضافة مفاتيح Supabase لصفحة البوتات (تحميل gmt-config بمفاتيح صريحة).
- **الخيار ج:** فصل الاختبارات: التي لا تحتاج قاعدة (فحص وجود البوتات) تعمل دائماً، والتي تحتاج قاعدة تُعلَّم بوضوح.

**الأفضل (مبدئياً):** الخيار أ + ج — رسالة واضحة + فصل الاختبارات، حتى تعمل الصفحة حتى بلا قاعدة.

## 🔴 مشكلة #3: الجرد لا يحمّل البيانات — «GMTCache is not defined» (خطير!)

### الصفحة
`03_INVENTORY/index_inventory.html` (الجرد)

### الدليل (من صورة المالك)
شريط أحمر أسفل الشاشة: «خطأ في التحميل: GMTCache is not defined» — والجرد يعرض «لا توجد منتجات» رغم وجودها.

### السبب الجذري (شخّصناه بدقة)
**مشكلة ترتيب تحميل:**
- كود الجرد يستدعي `GMTCache.syncCollection` عند التحميل (سطر ~3813) **بدون حماية** `if(window.GMTCache)`.
- لكن `gmt-core.js` (الذي يعرّف GMTCache) يُحمّل في **السطر 9548** (قرب نهاية الصفحة، 9552 سطر إجمالي).
- **النتيجة:** الجرد يستعمل GMTCache **قبل** أن يُحمّل → «not defined» → فشل تحميل المنتجات.

### لماذا حدث؟
عند دمج JS ونقل core لـ_shared، صار core يُحمّل بنهاية الصفحة. الصفحات الأخرى تحمّل مبكراً، لكن الجرد يستدعي GMTCache في كود يعمل عند التحميل المباشر.

### خطة التعديل المقترحة (3 خيارات)
- **الخيار أ (الأفضل):** نقل وسم `<script src="../_shared/gmt-core.js">` إلى **أعلى** الصفحة (في `<head>` أو أول `<body>`)، قبل أي كود يستعمل GMTCache. ينطبق على كل الصفحات للأمان.
- **الخيار ب:** حماية كل استدعاءات GMTCache بالجرد: `if(window.GMTCache){ ... }` مع بديل يحمّل مباشرة من Supabase لو GMTCache غير جاهز.
- **الخيار ج:** تأجيل كود الجرد حتى `DOMContentLoaded` + التأكد أن core محمّل أولاً.

**الأفضل:** الخيار أ — نقل core للأعلى بكل الصفحات (حل جذري، يمنع كل أخطاء «X is not defined» المشابهة).

### ⚠️ تحذير مهم للتعديل القادم
هذه المشكلة قد تكون **بكل الصفحات** التي تستعمل بوتات core مبكراً (ليس الجرد فقط). عند التعديل: تحقق من ترتيب تحميل core في كل صفحة، وانقله للأعلى.

## 🟡 طلب #2: تذكير مسح البيانات القديمة (للمرحلة القادمة)

### المطلوب
عند فتح **أي صفحة** بالنظام، تذكير فوري:
«امسح بيانات المتصفح القديمة» + دليل كيف يمسح من الإعدادات.

### خطة التنفيذ المقترحة
- إضافة بوت صغير `gmt-cache-notice.js` (أو ضمن gmt-core) يُظهر شريطاً علوياً أول مرة:
  «💡 لأفضل أداء، امسح بيانات المتصفح القديمة» + زر «كيف؟» يفتح تعليمات مصوّرة.
- يظهر مرة واحدة لكل نسخة (يُخزّن رقم النسخة بـlocalStorage).
- **الأفضل تقنياً:** تحديث رقم النسخة في `sw.js` (عامل الخدمة) بكل نشر → المتصفح يجلب الجديد تلقائياً دون مسح يدوي. نضيف تعليمات المسح كحل احتياطي فقط.

### تعليمات المسح (أندرويد) — للتوثيق
- **كروم:** ⋮ → إعدادات → الخصوصية → مسح بيانات التصفح → «الصور والملفات المخزّنة» → كل الأوقات.
- **PWA مثبّت:** اضغط مطولاً على الأيقونة → معلومات التطبيق → التخزين → مسح التخزين (أو احذف وأعد التثبيت).

## 🔴 مشكلة #3 (حرجة!): GMTCache is not defined — الجرد لا يحمّل

### الصفحة
`03_INVENTORY/index_inventory.html` (الجرد)

### الخطأ الظاهر
«خطأ في التحميل: GMTCache is not defined» + الجرد لا يعرض المنتجات (0 منتج).

### السبب الجذري (مؤكّد بالفحص)
`GMTCache` معرّف داخل `gmt-core.js`، لكن **ترتيب التحميل خاطئ**:
- كود الجرد يستدعي `GMTCache.syncCollection()` في دالة `loadProducts()` بسطر **3813**.
- `loadProducts()` تُنادى وقت تحميل الصفحة.
- لكن `gmt-core.js` يُحمّل بسطر **9548** (آخر الصفحة) — **بعد** أن تعمل loadProducts.
- النتيجة: الجرد يحاول استعمال GMTCache قبل تحميله → ينكسر.

### السبب الأصلي
عند الدمج ونقل gmt-core إلى _shared، صار وسم `<script src="../_shared/gmt-core.js">` **بآخر الصفحة** بدل أن يكون **بالبداية (بالـ<head> أو أول الجسم)**.

### خطة التعديل (للتنفيذ لاحقاً)
**الحل:** نقل وسم تحميل `gmt-core.js` (و`gmt-staff.js`) إلى **بداية الصفحة** (بالـ<head> أو أول <body>)، قبل أي كود يستعمل GMTCache.
- **مهم:** هذه المشكلة قد تكون بصفحات أخرى أيضاً (أي صفحة تستعمل GMTCache أو بوتاً من core في كودها المبكر).
- **يجب فحص كل الصفحات** للتأكد أن core يُحمّل مبكراً.
- **بديل أسرع:** إضافة حماية `if(window.GMTCache)` قبل كل استدعاء + إعادة المحاولة، لكن الأصح نقل التحميل للأعلى.

### الصفحات المطلوب فحصها (نفس المشكلة محتملة)
كل صفحة تحمّل core بآخرها وتستعمله مبكراً: الجرد (مؤكّد) · وربما نقطة البيع · المشتريات · الأوردرات.

## 🚨 اكتشاف موحّد: مشكلة ترتيب التحميل في كل الصفحات (20 صفحة)

### الحقيقة المكتشفة
`gmt-core.js` و `gmt-staff.js` مُحمّلان **بآخر كل صفحة** (وسم الـ<script> انتقل للنهاية عند الدمج) — في **كل الـ20 صفحة**.

### لكن ليست كلها تنكسر
- **تنكسر:** الصفحات التي يستعمل كودها core/GMTCache/بوتاً مبكراً (عند DOMContentLoaded أو أعلى الكود). مؤكّد: الجرد (GMTCache) · المتجر (الموشن).
- **تعمل:** الصفحات التي لا تعتمد على core في كودها المبكر (core يصل قبل أن يُستعمل فعلياً).

### الحل النهائي (إصلاح واحد لكل شيء)
**نقل وسمَي `gmt-core.js` و `gmt-staff.js` إلى بداية كل صفحة** (داخل <head>، بعد ضبط مفاتيح Supabase مباشرة، قبل أي سكربت آخر).

### خطة التنفيذ الآمنة (للمراجعة)
1. لكل صفحة: احذف وسمَي core/staff من آخر الصفحة.
2. أضفهما بالـ<head> (أو أول <body>) — بعد إعداد المفاتيح.
3. **استثناء:** إذا كانت المفاتيح (gmt-config) تُضبط بكود inline بالصفحة، تأكد أن core يأتي بعدها.
4. افحص كل صفحة بعد التعديل (jscheck + فتح حي).

### لماذا حدث هذا؟
عند الدمج، كان معظم البوتات تُحمّل بآخر الصفحة أصلاً (وهذا مقبول للبوتات لأنها تعمل بعد التحميل). لكن `gmt-cache` (GMTCache) و`gmt-config` (المفاتيح) **يجب أن يُحمّلا مبكراً** لأن كود الصفحة يعتمد عليهما فوراً. الدمج وضعهما ضمن core بالنهاية → المشكلة.

### حل بديل محتمل (أنظف)
فصل الأجزاء الحرجة المبكرة (gmt-config + gmt-cache) في ملف صغير `gmt-boot.js` يُحمّل بالـ<head>، وإبقاء باقي البوتات بآخر الصفحة.
- ميزة: تحميل أسرع + لا تنكسر الصفحات.
- عيب: ملف إضافي (لكن صغير).

**القرار للمالك:** نقل core كامل للأعلى (أبسط) أم فصل gmt-boot (أنظف).

## 🔴 مشكلة #5: التقارير تسجّل «نجح/فشل» فقط — بلا تفاصيل (ماذا · لماذا)

### الملاحظة
التقارير تعرض النتيجة (✅/🔴) والعنوان فقط، دون شرح: ماذا صار · ما العطل · لماذا حدث.

### التشخيص (3 مستويات)

**المستوى 1 — العرض (صفحة البوتات 19_PROTECTION، دالة run-all):**
- 🔴 الفاحص الشامل (AutoTest): يطبع `x.title` فقط — بلا `x.msg`.
- 🔴 الفاحص الذاتي (SelfTest): يطبع `x.title` فقط — بلا `x.msg` ولا `x.detail`.
- ✅ الحارس + الترابط: يطبعان `x.msg` (صحيح).

**المستوى 2 — هل البوتات تخزّن التفاصيل؟**
- ✅ نعم. الحارس يحفظ (what/how/why/detail). المفتّش يحفظ (msg/detail/reason).
- **التفاصيل موجودة بالتخزين، لكن لا تُعرض كلها.**

**المستوى 3 — المصبّ الموحّد (master-report):**
- ✅ أفضل — يطبع «كيف فُحص» و«النتيجة» (c.how, c.detail).
- لكن البوتات التي يجمعها قد لا تمرّر تفاصيل كافية إليه.

### السبب الجذري
**فجوة بين التخزين والعرض:** البوتات تخزّن التفاصيل، لكن كود عرض التقرير (خاصة الفاحص الشامل والذاتي بصفحة البوتات) يطبع العنوان فقط ويهمل msg/detail/why.

### خطة التعديل (للتنفيذ لاحقاً)
1. **بصفحة البوتات (run-all):** أضف `+ ' — ' + (x.msg||x.detail||'')` للفاحص الشامل والذاتي (مثل الحارس).
2. **بكل بوت:** تأكد أن كل نتيجة تتضمن:
   - `what` (ماذا صار)
   - `why` (لماذا / السبب المحتمل)
   - `how` (كيف فُحص)
   - `msg/detail` (التفاصيل الفنية)
3. **بالمصبّ الموحّد:** تأكد أنه يجمع ويعرض كل هذه الحقول من كل بوت.
4. **الهدف:** كل خطأ بالتقرير يجب أن يجيب: ماذا صار؟ أين؟ لماذا؟ كيف نصلحه؟

### مثال للشكل المطلوب (بدل «🔴 فشل الاختبار»):
```
🔴 فشل اختبار الكتابة
   ماذا: محاولة كتابة صف تجريبي في error_log فشلت.
   لماذا: الجدول غير موجود أو صلاحيات RLS تمنع الكتابة.
   كيف نصلح: شغّل SQL الخاص بـerror_log، أو راجع سياسات RLS.
```

### الأولوية: عالية
هذا جوهر طلب المالك: «التقرير يشرح كل شيء» — ليأخذه أسبوعياً ويناقشه.
